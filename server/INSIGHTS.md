# server — Engineering Insights

Verified, non-obvious knowledge for `server/`. Append-only; maintained via the `engineering-insights` skill.

### 2026-10-11 — Client copy of @devdigest/shared lags the server copy; diff before reusing a contract in the client
- **Category:** Codebase Patterns
- **Status:** verified
- **Discovery:** `server/src/vendor/shared` (used by server + reviewer-core) and `client/src/vendor/shared` are hand-maintained copies with no sync check, and the client copy is behind: in every differing file the server side has the newer additions. Concretely, the client's `PluginAgent.provider` rejects `'openrouter'`, although `agents.provider` and the shared `Provider` enum allow it — so an OpenRouter agent would fail client-side validation once plugin export/import (L08) uses this schema.
- **Evidence:** `server/src/vendor/shared/contracts/productionize.ts:36` (`PluginAgent.provider`) — `z.enum(['openai', 'anthropic', 'openrouter'])`; `client/src/vendor/shared/contracts/productionize.ts:36` — `z.enum(['openai', 'anthropic'])`; `client/src/vendor/shared/contracts/knowledge.ts:155` (`Provider`) already includes `'openrouter'`; `server/src/db/schema/agents.ts:15` allows `'openrouter'`; `client/src/vendor/shared/adapters.ts:77` (`LLMProvider.id`) also lacks `'openrouter'` vs `server/src/vendor/shared/adapters.ts:83`. `diff -rq client/src/vendor/shared server/src/vendor/shared` → 5 differing files: `adapters.ts`, `contracts/eval-ci.ts`, `contracts/knowledge.ts`, `contracts/productionize.ts`, `contracts/trace.ts` (`trace.ts`: comments only). `PluginAgent` has no consumers outside `vendor/shared` yet (grep).
- **Guidance:** Treat the server copy as the newer one. Before using a shared schema in the client, `diff` the two files; when changing a contract, update both copies in the same change and re-run `diff -rq`. Prefer `Provider` over re-declared provider enums.
- **Cross-package:** `client/` consumes the stale copy (types + runtime Zod validation); `reviewer-core/` aliases the server copy (`reviewer-core/tsconfig.json`), so it is unaffected.

### 2026-10-11 — Review runs bypass JobRunner; restart recovery is only a boot-time "running → failed" reaper
- **Category:** Codebase Patterns
- **Status:** verified
- **Discovery:** `agent_runs` rows are inserted directly as `'running'` (there is no `queued` state) and executed fire-and-forget in-process, NOT via `JobRunner`/`jobs`. On restart nothing resumes: `buildApp` awaits a reaper that flips every `'running'` row to `'failed'` without `error`, `durationMs` or a `run_traces` row, and the reaper assumes a single API instance per DB. The in-memory `RunBus` is empty after restart, so an SSE subscriber to a pre-restart run gets no replay and no `done` (stream stays open until the client disconnects).
- **Evidence:** `server/src/modules/reviews/repository/run.repo.ts:134` (`createAgentRun`) — `status: 'running'`; `server/src/modules/reviews/service.ts:133` (`runReview`) — `void this.executor.executeRuns(...)`; `server/src/modules/reviews/repository/run.repo.ts:104` (`reapStaleRunningRuns`) — `.set({ status: 'failed' })` only; `server/src/app.ts:78-81` — single-instance NOTE + awaited reap before routes; `server/src/platform/sse.ts:93` (`onDone`) — fires only if `completed.has(runId)` (in-memory); `server/src/db/schema/runs.ts:21` — `status: text('status')` (no enum/check); `server/src/platform/jobs.ts:59` (`JobRunner.enqueue`) — `jobs` rows have no reaper either.
- **Guidance:** Don't add a `queued` state or a resume path without also changing the reaper (it would reap/miss them). If you touch the reaper, set an `error` (e.g. "server restarted") so the UI can explain the failure. Multi-replica deployment needs per-instance ownership/heartbeats first. Reviews/findings are persisted before `completeAgentRun`, so a crash in between leaves a review attached to a run later reaped as `failed`.
- **Cross-package:** `client/` relies on `/pulls/:id/runs/active` (DB status) as the source of truth for in-flight runs.

### 2026-10-11 — Cancelling a live run clears its own cancel flag; a finished runner can overwrite 'cancelled'
- **Category:** What Doesn't Work
- **Status:** verified
- **Discovery:** `ReviewService.cancelRun` calls `runBus.cancel(runId)`, awaits the DB update, then `runBus.complete(runId)` — and `complete()` deletes the run from the `cancelled` set. A live runner only checks the flag at `checkCancelled()` before each LLM chunk, so unless that checkpoint happens during the awaited DB update it never sees the cancel; the run keeps going and `completeAgentRun` (unconditional `WHERE id = runId`) then overwrites `'cancelled'` with `'done'`/`'failed'`. Verified by code read, not by a test.
- **Evidence:** `server/src/modules/reviews/service.ts:85-90` (`cancelRun`); `server/src/platform/sse.ts:79` (`RunBus.complete`) — `this.cancelled.delete(runId)`; `reviewer-core/src/review/run.ts:164` — sole `checkCancelled` checkpoint; `server/src/modules/reviews/repository/run.repo.ts:159-172` (`completeAgentRun`) — no status guard; `server/src/modules/reviews/run-executor.ts:209-211` — `isCancelled` check.
- **Guidance:** When changing cancel/recovery logic, keep the cancel flag until the runner exits (or track it separately from `complete`), and guard terminal writes with `status = 'running'` so terminal states aren't overwritten. Add an `.it.test.ts` covering cancel-during-run before relying on it.
- **Cross-package:** `reviewer-core/` owns the checkpoint placement (`reviewPullRequest`).

### 2026-10-11 — Success is now one guarded transaction; terminal states can no longer be overwritten
- **Category:** Codebase Patterns
- **Status:** verified
- **Supersedes (pending review):** "Cancelling a live run clears its own cancel flag; a finished runner can overwrite 'cancelled'" (the overwrite half) and the last Guidance sentence of "Review runs bypass JobRunner; …" (reviews/findings are no longer persisted before the status write).
- **Discovery:** The executor no longer calls `completeAgentRun`. A successful run is finalized by `finalizeDoneRun`: one transaction whose FIRST statement is `UPDATE … SET status='done' … WHERE status='running'`, followed by the review, findings, `last_reviewed_sha` and the trace. A cancel committed first makes the claim match 0 rows and nothing is written. Failure/cancel use guarded `recordRunFailed` / `recordRunCancelled`, so `cancelled`/`done` are never overwritten. Still true: `RunBus.complete` clears the cancel flag, so a live runner keeps calling the LLM after a cancel (its result is then discarded).
- **Evidence:** `server/src/modules/reviews/repository/run.repo.ts:247` (`finalizeDoneRun` claim), `:280` (`recordRunFailed`), `:311` and `:321` (`recordRunCancelled` A / B with `error IS NULL`); `server/src/modules/reviews/run-executor.ts:287` (`finalizeDoneRun` call), `:343` (`reconcileTerminal`); `server/src/platform/sse.ts:79` (`cancelled.delete`). `DATABASE_URL=postgres://guard@127.0.0.1:1/do_not_use pnpm exec vitest run test/run-finalize.it.test.ts test/run-executor-finalize.it.test.ts` → 26/26 pass, incl. R9/R10 (claim vs. cancel race) and E5 (cancel just before the claim).
- **Guidance:** Never write a terminal status without `WHERE status = 'running'` (or the `cancelled` + `error IS NULL` annotate form). After a failed success transaction, decide the published event from the guarded write's result, not from the exception — the commit may have succeeded (spec `server/specs/review-run-cost.md` §3.7).

### 2026-10-11 — Existing `*.repo.ts` functions run unchanged inside a Drizzle postgres-js transaction
- **Category:** Tool & Library Notes
- **Status:** verified
- **Discovery:** `PostgresJsTransaction` is assignable to `Db` (`PostgresJsDatabase<typeof schema>`), so repo functions typed `(db: Db, …)` accept `tx` with no signature change. `db.transaction` reserves one connection via postgres-js `begin` (throw → ROLLBACK); calling `.transaction` on a `tx` becomes a SAVEPOINT, so a function that opens its own transaction still composes inside an outer one. `SET LOCAL lock_timeout/statement_timeout` inside a transaction bounds its statements without touching the pool's global settings.
- **Evidence:** `node_modules/drizzle-orm/postgres-js/session.js:96-97` (`transaction` → `this.client.begin`); `server/test/run-finalize.it.test.ts:244` — `finalizeDoneRun(tx, …)` (itself `db.transaction`) inside an outer `db.transaction`, passes; `server/src/modules/reviews/repository/run.repo.ts:360-368` (`withLocalTimeouts`). A scratch `tsc` passing `tx` to `insertReview` / `saveRunTrace` compiled; passing a `string` failed with TS2345.
- **Guidance:** To make several repo writes atomic, wrap them in `db.transaction(async (tx) => …)` and pass `tx`. Never `await` an LLM or other slow I/O inside the callback: it holds a pooled connection (`max: 10`).

### 2026-10-11 — Integration tests still see the dev `DATABASE_URL`, real secrets and real GitHub unless overridden
- **Category:** What Doesn't Work
- **Status:** verified
- **Discovery:** `config.ts` imports `dotenv/config`, so under Vitest `process.env.DATABASE_URL` is the dev DB from `server/.env`. `buildApp` ignores it only when `db` is passed. `Container` defaults to `LocalSecretsProvider` (`~/.devdigest/secrets.json`), and `container.github()` reads `GITHUB_TOKEN` from it, so a test hitting `GET /repos/:id/pulls` without `github`/`secrets` overrides can call real GitHub with the developer's token. `MockGitHubClient()` with default options upserts PR #482 into the repo being listed, which collides with fixtures that also use number 482.
- **Evidence:** `server/src/platform/config.ts:1` (`import 'dotenv/config'`); `server/src/app.ts:43` (`opts.db ? null : createDb(config.databaseUrl)`); `server/src/platform/container.ts:83` (`LocalSecretsProvider` default), `:156` (`secrets.get('GITHUB_TOKEN')`); `server/test/run-cost-api.it.test.ts:62-63` — the safe override set. A run with `DATABASE_URL=postgres://guard@127.0.0.1:1/do_not_use` passed 47/47 integration tests, so none of them used the dev DB.
- **Guidance:** In DB-backed tests always pass `db: pg.handle.db`, plus `secrets: new MockSecretsProvider({})` and `github: new MockGitHubClient({ pulls: [] })` when a route may sync from GitHub. Run integration lanes with a guard `DATABASE_URL`: dotenv does not override variables that are already set.

### 2026-10-15 — Drizzle leaves columns unqualified in a single-table select, so a correlated `sql` subquery binds to the wrong table
- **Category:** Tool & Library Notes
- **Status:** verified
- **Discovery:** When the outer query selects from ONE table without joins, Drizzle renders every column reference without its table name, including the ones interpolated into a `sql` template. A correlated subquery such as ``sql`(select count(*) from ${t.agentSkills} inner join ${t.agents} on ${t.agents.id} = ${t.agentSkills.agentId} where ${t.agentSkills.skillId} = ${t.skills.id})` `` therefore compares `skill_id` with the inner `agents.id` (the closest `"id"` in scope), not with `skills.id`. The query runs without an error and silently returns 0.
- **Evidence:** `.toSQL()` of that query printed `select "id", (select count(*) from "agent_skills" inner join "agents" on "id" = "agent_id" where "skill_id" = "id") from "skills" where "skills"."workspace_id" = $1`. The first version of `agent_count` failed `server/test/skills.it.test.ts:94` (S3: `expected +0 to be 2`). The fix is in `server/src/modules/skills/repository.ts:27` (`selectWithCount`): a grouped subquery `.as('agent_counts')` LEFT JOINed and read with `coalesce(${counts.n}, 0)` (`:39`). With it, S1–S8 pass (8/8).
- **Guidance:** Don't write correlated subqueries with interpolated columns in a single-table select. Instead, aggregate in a grouped subquery and join it, add a join (Drizzle then qualifies columns), or spell the outer column out with `sql.raw('"skills"."id"')`. Check suspicious SQL with `.toSQL()`, and cover every count or aggregate with an `.it.test.ts`; unit tests cannot catch this.
